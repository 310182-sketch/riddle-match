# 決策紀錄

## 本分支的產品方向

- **狀態：** 本分支採用；與遠端 main 的產品方向不同。
- **現況：** 遠端 main 是陌生人自由提問的猜謎遊戲；目前工作區的 knowledge/plan.md 是二選一共同點遊戲。
- **決定：** 依照目前計畫與最新指示製作二選一共同點原型，不把自由聊天或猜謎流程帶入本分支。
- **推薦：** 保留 main 不動，以 codex/commonality-quiz-prototype 分支呈現這次方向。確認產品方向一致後，再決定是否將本分支合併到 main。
- **適用範圍：** 目前原型及其下一階段；若使用者指定回到猜謎產品，需先調整本計畫和原型方向。

## 二選一原型預設

- **狀態：** 已採用，適用於互動原型；可依玩家回饋調整。
- **決定：** 每局配對兩位玩家，主題在旅行、音樂、日常、飲食中擇一；也可隨機抽一種。一局五題，每題兩個選項；雙方都答完才揭曉。結果頁顯示相同答案的題數和共同選擇。
- **決定：** 原型以免註冊和一次性暱稱進場；目前不實作社群登入、自由聊天、遊戲紀錄或排行榜。
- **原因：** 先讓使用者能走完選主題、配對、逐題作答與結果回顧，驗證核心玩法，再投入真人即時服務。
- **適用範圍：** 瀏覽器互動原型，不代表正式版的題數、配對逾時、資料保存或登入規格。

## 示範配對方式

- **狀態：** 已採用於原型。
- **決定：** 由本機範例資料提供示範對象及其選擇。畫面需清楚標示示範模式，且暱稱和作答不保存。
- **原因：** 可以在不建置即時後端的情況下預覽逐題揭曉和結果流程。
- **限制：** 不代表真人配對、雙人同步、離線處理或正式答案判定已完成。

## 真人配對與房間同步

- **狀態：** 採用為下一階段的實作預設；尚未建立或連接 Supabase 專案。
- **決定：** 使用 Supabase Anonymous Auth 驗證玩家，以 PostgreSQL RPC 原子配對及提交答案，並透過 Realtime 通知房間狀態更新。
- **安全規則：** 答案由資料庫保存；RPC 只在同房兩位玩家都完成作答後回傳雙方答案。前端不直接讀取答案資料表，也不放入 service role key。
- **原因：** 保留 GitHub Pages 靜態前端，不需先維護常駐伺服器；需要的配對、資料權限和房間通知可由同一個託管服務提供。
- **未完成條件：** 建立 Supabase 專案，套用並驗證 migration，設定公開用戶端 URL/key，並檢查匿名登入、RLS 與 Realtime 權限。
- **適用範圍：** 兩位玩家的真人 MVP。社群登入平台、資料保留和安全措施另行決定。

## 正式配對和帳號細節

- **狀態：** 採用於真人 MVP 的暫定預設，需在實際上線前驗證。
- **決定：** 一局兩人、五題、固定一個主題；兩人選不同的指定主題時不配對，選「隨機」可和任何主題配對並沿用對方的指定主題，兩人都選隨機時由系統抽題。等待上限先設三十秒，逾時可重新排隊或離開。
- **決定：** 一開始使用匿名登入和一次性暱稱，不保留完整遊戲紀錄；先不做排行榜或自由聊天。
- **推薦：** 以同一瀏覽器的示範原型收集流程回饋後，再調整題數、等待時間和紀錄政策；匿名身分不得當作可靠的防濫用機制。
- **適用範圍：** 真人 MVP 的初始規格，不代表長期產品承諾。

## 社群登入與資料保存

- **狀態：** 未決定，後端原型不受阻塞。
- **待決事項：** 確認是否要提供社群登入、需支援的平台、匿名帳號升級方式、房間清除時限和檢舉／封鎖流程。
- **推薦：** 先驗證匿名配對遊戲，再依需求逐一確認 Google、LINE、Apple、Facebook、Instagram、Threads 和 X 的官方限制與成本。
- **適用範圍：** 真人 MVP 之後的帳號與信任安全功能。
