# 專案經驗

## 排程清理與匿名服務的限流界線

- **經驗：** 只靠訪客請求觸發的清理，在服務閒置時可能不會執行；排程應限制單次工作量、記錄結果並讓失敗重試。全站共用限額則可能被少數來源耗盡；逾時和每人限流只能降低部分風險，不能取代可信的邊緣防濫用。
- **適用範圍：** 使用 serverless API 保存匿名 session、聊天或其他需定期刪除資料的服務。
- **本專案做法：** 實作只接受 Neon 排程事件的獨立清理 Function，保留惰性清理作備援；API 限制請求讀取時間，並避免無效 token 消耗已登入玩家的共用額度。排程尚未部署，正式公開前仍需邊緣防濫用和監控。

## 在 Neon SQL Editor 安全套用多語系遷移

- **經驗：** SQL Editor 可依序執行交易內的多條指令，但大型查詢的歷史紀錄可能被截斷；以 UTF-8 傳遞並在執行前比對完整內容，再用唯讀檢查和回滾交易驗證，能降低編碼錯誤與留下測試資料的風險。
- **適用範圍：** 透過管理介面部署含非 ASCII 內容的 PostgreSQL schema 或函式。
- **本專案做法：** 在使用者指定的 Neon `neondb` 以交易依序套用基礎與封鎖遷移；核對 RLS 標記及中文主題，使用兩個臨時玩家測試配對與封鎖後回滾。Functions 與瀏覽器端到端仍待驗證。

## Pages 發布檔案可能延遲出現在部署 API

- **經驗：** 網站 artifact 上傳步驟成功後，部署步驟仍可能暫時查不到同一次工作流程的 artifact。應查看失敗工作與 log，確認是檔案索引延遲後再重試，並讓第二次失敗仍明確使部署失敗。
- **適用範圍：** 透過 GitHub Actions 上傳 artifact 並部署 GitHub Pages 的工作流程。
- **本專案做法：** Pages 在測試成功後上傳網站；第一次部署失敗時等待十秒重試一次，部署網址取成功步驟的結果。自動化測試失敗時不會部署。

## 匿名配對的封鎖範圍與競態

- **經驗：** 匿名遊戲無法保證辨識換了新身分的同一個人，因此封鎖範圍必須清楚告知。封鎖與配對若同時進行，應使用一致的鎖順序，並由伺服器從房間推導對手，避免偽造目標或剛封鎖又配回同一人。
- **適用範圍：** 沒有持久帳號、使用暫時 session 配對的聊天室或多人遊戲。
- **本專案做法：** Neon 版以資料庫交易封鎖目前匿名身分並離開房間，配對時雙向排除封鎖組合；重試不影響其他房間，測試涵蓋權限及並行。更換匿名身分後不保證繼續封鎖，且真人環境尚未驗證。

## 將平台專屬即時後端移植至 Neon

- **經驗：** 雖然託管資料庫都使用 PostgreSQL，認證函式、角色、資料表和即時廣播未必相容。移植時需重新建立可信的身分驗證與私有資料邊界，而不是讓瀏覽器直接持有資料庫憑證。短輪詢與過期心跳可先提供狀態同步，但清理若由請求觸發，閒置期間不保證準時完成。
- **適用範圍：** 將靜態前端搭配的即時互動服務遷移至 Neon 或其他 PostgreSQL 平台。
- **本專案做法：** Neon 遷移使用獨立 schema，Functions 只接受固定 API，匿名 session 僅儲存雜湊，經授權後在交易內設定玩家身分；以 PGlite、瀏覽器整合與 PostgreSQL 多連線測試確認本機行為。正式部署及公開服務防濫用仍待驗證。

## 發布前自動執行跨層測試

- **經驗：** 前端、API 與遷移分開通過測試，仍可能因呼叫參數或狀態契約不同而整合失敗。將主要客戶端測試、資料庫測試與跨層測試放在發布工作之前，可避免失敗版本覆蓋已發布網站。
- **適用範圍：** 前端與後端共用版本庫、由 GitHub Actions 發布靜態網站的專案。
- **本專案做法：** Pages workflow 先執行 Node 與本機 PostgreSQL 相容環境的測試，通過後才上傳網站；真實 Neon 環境和獨立訪客仍需另外驗證。

## 畫面切換與延遲回覆的生命週期

- **經驗：** 即使是展示用的延遲回覆，也可能在離開或換輪後寫入新的畫面，或在時間到後才判定答對。將回覆綁定目前回合、結束後忽略過期回呼，並在畫面切換時移動焦點，可讓互動和鍵盤操作維持一致。
- **適用範圍：** 有計時、模擬回覆或非同步動作的單頁互動網站。
- **本專案做法：** 展示版以回合識別排除過期回覆，逾時即結束判定，切換頁面時將焦點移至標題；用瀏覽器檢查倒數、逾時和跨輪情境。

## 非同步遊戲操作要綁定回合與伺服器時間

- **經驗：** 延遲抵達的出題、猜題或換輪請求可能在下一輪誤執行；重連後只補訊息也會漏掉房間狀態。操作應攜帶發起時的回合號並在鎖定房間後驗證，逾時應以取得鎖後的伺服器時間判斷，重新連線則須補讀狀態與訊息。
- **適用範圍：** 多人遊戲、配對及其他會因網路延遲而重試的狀態機。
- **本專案做法：** 在保留的 Supabase 原型加入回合號檢查、離開與重連處理，並以 PGlite 和模擬前端測試回歸；移植到 Neon 後仍需要真實多連線及雙訪客驗證。

## 跨畫面調整品牌色與響應式版面

- **經驗：** 主色變更不只影響按鈕，還要一併檢查背景、邊框、狀態、文字對比及鍵盤焦點；桌面、平板和窄手機的首頁、等待頁與遊戲房間都應實際操作。手機輸入文字達 16px 可減少部分瀏覽器輸入時自動放大。
- **適用範圍：** 同一套品牌視覺涵蓋多畫面和表單的響應式網站。
- **本專案做法：** 改用藍白色系，重整畫面層級及間距，並在 320、375、768 與 1440px 檢查展示互動；完整無障礙稽核及真人模式驗證仍待完成。

## 跨前端與資料庫的主題庫一致性

- **經驗：** 同一組內容若分別寫在展示前端、配對 RPC 與換輪 RPC，修改時容易出現數量或順序不一致；內容準則、人工審查與自動一致性檢查需要一起規劃。已部署的資料庫遷移應以新的向前遷移變更，避免不同環境的歷史版本不一致。
- **適用範圍：** 靜態展示版與伺服器正式版分開保存同一組分類、選項或遊戲內容的產品。
- **本專案做法：** `knowledge/topic-policy.md` 記錄主題準則和審查、發布及下架流程；`tests/topics.test.mjs` 檢查展示版與遷移中最新的配對及換輪主題清單一致性。正式內容發布仍須人工審查及實際環境測試。

## GitHub Pages 適用於靜態前端

- **經驗：** GitHub Pages 會託管靜態檔案，適合先發布前端雛形；它本身不提供配對佇列、即時聊天室、共享遊戲狀態或答案驗證服務。
- **適用範圍：** 使用 GitHub Pages 發布需要多位訪客即時互動的網站時，先標示展示模式，再規劃獨立的即時後端或託管服務。
- **本專案做法：** 以瀏覽器內模擬流程呈現產品概念，真人配對列為後續路線圖項目。

## 專案型 Pages 部署

- **經驗：** 專案頁面通常部署在 `/<repository>/` 子路徑，HTML 引用 CSS、JavaScript 和圖片時使用相對路徑，可避免硬編碼網域根目錄造成資源 404。
- **適用範圍：** 發布至 `https://<owner>.github.io/<repository>/` 的靜態網站。
- **本專案做法：** 網站檔案集中在 `site/`，資源引用採相對路徑；Actions workflow 上傳 `site/` artifact，再交由 Pages 部署 action 發布。

## GitHub Actions 部署 Pages

- **經驗：** 使用官方 Pages actions 時，workflow 需要 `pages: write` 和 `id-token: write` 權限；repository 的 Pages source 需設為 GitHub Actions。
- **適用範圍：** 透過 GitHub Actions 將靜態檔案發布到 GitHub Pages。
- **本專案做法：** push 到 `main` 或 `master` 時執行部署，並保留手動觸發入口。

## GitHub Actions runner 執行環境警告

- **經驗：** 部署 action 即使尚能執行，也可能先出現執行階段棄用警告；部署失敗時應查看失敗步驟的 annotation，再區分警告和真正錯誤，並參照官方 release 更新主要版本。
- **適用範圍：** 使用 GitHub Actions 的網站部署與持續整合 workflow。
- **本專案做法：** Pages workflow 從 checkout v4、configure-pages v5、upload-pages-artifact v3 和 deploy-pages v4 更新至查得的目前主要版本；首次失敗的實際原因是 Pages 在 workflow 啟動時尚未啟用。

## 即時遊戲狀態與答案保護

- **經驗：** 靜態前端中的答案只適合展示原型；任何送到瀏覽器的程式與資料都能被玩家檢視。真人遊戲應由伺服器保管謎底並判定答案，伺服器也應作為計時與回合切換的權威來源。
- **適用範圍：** 有隱藏答案、競賽結果、倒數或多位玩家共享狀態的瀏覽器遊戲。
- **本專案做法：** 單機展示版以 JavaScript 模擬答案判定；出題者輸入謎題和謎底的介面可展示流程，但答案目前仍會送到瀏覽器。接上真人配對服務前，需把謎底和回合狀態移到後端。

## 使用 RLS 保護房間內的祕密欄位

- **經驗：** Postgres Row Level Security 控制資料列的讀取，不會隱藏同一列中的個別欄位。若兩位房間玩家都能讀取房間資料列，將答案放在該列就會把答案一併暴露給猜題者。應將答案放進獨立資料表，以 RLS 限制直接讀取，再用檢查房間角色的 RPC 執行答案判定及逾時揭曉。
- **適用範圍：** 多位使用者共享遊戲房間，但其中只有部分角色可讀取答案、提示或其他私有資料的應用。
- **本專案做法：** `match_rooms` 只存可供雙方閱讀的謎題和狀態；`room_secrets` 保存答案和提示。猜題者透過 `submit_guess` 只取得正誤結果，逾時後再由 `end_expired_round` 取得答案。此遷移尚待套用至 Supabase project 並核對權限。

## 以資料庫交易鎖保護配對佇列

- **經驗：** 多個配對請求可能同時選取同一位等待者。將配對選擇、刪除佇列項目和建立房間放在單一資料庫 RPC 交易內，並用交易層級鎖序列化佇列操作，可避免兩個請求都配走同一位玩家。取消等待也必須使用相同鎖，才能處理配對與取消同時發生的情況。
- **適用範圍：** 多用戶佇列、工作領取或其他要求同一資源不可被同時分配兩次的資料庫流程。
- **本專案做法：** `join_matchmaking` 和 `cancel_matchmaking` 共用交易層級 advisory lock，配對在同一個交易中刪除雙方等待項目並建立房間；取消請求亦會結束剛完成配對的房間。

## 靜態網站的選用式即時後端

- **經驗：** 靜態展示頁面可以保留作為無設定的本機預覽，同時提供可選的即時後端模式。只有明確填入公開服務 URL 與用戶端 key 時才載入即時服務 SDK；空白設定繼續走展示流程。公開 key 仍必須依賴 RLS，不可當作祕密或授權檢查。
- **適用範圍：** 需要以靜態網站主機逐步接入託管式即時服務，且希望開發預覽不依賴服務設定的產品原型。
- **本專案做法：** `site/boot.js` 依 `site/supabase-config.js` 選擇真人流程或示範流程。前端設定只預留公開 URL 與 key，真人模式仍待實際部署及跨訪客驗證。

## 平板寬度先堆疊主內容與側欄

- **經驗：** 桌面雙欄介面在約 850px 的可用寬度仍可能把主操作區和說明側欄都擠窄，造成表單與文字難讀；只在手機斷點堆疊會太晚。應在內容開始受擠壓的平板／窄桌面寬度先改成單欄，再保留更小螢幕的專屬簡化樣式。
- **適用範圍：** 主要互動區旁有次要導覽、說明或設定面板的響應式網站。
- **本專案做法：** 依公開版約 856px 寬的房間畫面，將猜謎房間的單欄斷點提前至 900px；說明步驟在該寬度橫向排列，讓主要遊戲卡片保有閱讀寬度。

## 靜態網站的憑證邊界

- **經驗：** GitHub Pages 發布的前端內容是公開可讀的，不可把 Personal Access Token、服務角色金鑰或其他伺服器祕密放進 HTML、JavaScript、建置產物或公開 repository。
- **適用範圍：** GitHub Pages 或其他靜態主機搭配第三方後端服務的網站。
- **本專案做法：** 尚未加入任何服務金鑰；選定即時後端後，前端只使用允許公開的用戶端設定，並由後端存取規則保護房間和資料。

## GitHub 網頁登入與本機 Git 授權

- **經驗：** 在瀏覽器登入 GitHub 不會自動為 Git 命令列設定 push 權限；Windows 上可使用 Git Credential Manager 完成一次 OAuth 授權，避免把 Personal Access Token 貼進聊天或原始碼。
- **適用範圍：** 使用 Git for Windows 從本機建立遠端 repository、push commit 或查詢 GitHub Actions 時。
- **本專案做法：** 透過 Git Credential Manager 授權 `310182-sketch`，設定本機 repository 使用 `manager` helper，再建立 `origin` 並推送。
